# Обзор Visa Research Workflow

## 1. Назначение

Visa Research Workflow помогает исследовать вопросы о визах и иммиграции
США с помощью локальной языковой модели. Система не просит модель отвечать
только по памяти. Для каждого содержательного вопроса она:

1. строит самостоятельный поисковый запрос;
2. находит и загружает документы с разрешённых государственных доменов;
3. передаёт документы исследующему агенту через ограниченные инструменты;
4. проверяет использованные идентификаторы источников;
5. повторно сверяет выводы с evidence;
6. формирует ответ и применяет финальные программные проверки.

Есть два режима работы:

- интерактивный CLI для последовательного диалога;
- benchmark runner для одинаковых, измеряемых и воспроизводимых запусков.

## 2. Что система контролирует программно

Языковая модель отвечает за понимание вопроса, поиск релевантных фрагментов
в уже загруженных документах и формулировку текста. Python-код отвечает за
условия, которые нельзя оставлять на усмотрение модели:

- поиск является отдельным обязательным шагом;
- принимаются только HTTPS URL с разрешённых доменов;
- переходы по redirect повторно проверяются до внешнего запроса;
- размер ответа и объём извлечённого текста ограничены;
- каждый документ и весь evidence package получают SHA-256;
- Researcher и Validator обязаны реально прочитать evidence;
- source IDs проверяются относительно пакета текущего запуска;
- Validator не может добавить новый URL или источник;
- финальный ответ не может потерять обязательные цитаты или добавить новые;
- URL в ответ добавляются только программно из проверенного пакета;
- юридический disclaimer добавляется детерминированно;
- известные практические советы по подделке и мошенничеству блокируются;
- ошибка обязательного шага останавливает pipeline.

Эти проверки уменьшают риск неподтверждённых ответов, но не доказывают
юридическую правильность каждого вывода.

## 3. Требования

- Python 3.12 или новее;
- Ollama, доступный по HTTP API;
- локальная модель с заявленной поддержкой `tools`;
- интернет для поиска и загрузки официальных документов;
- Git — необязателен для диалога, но нужен для точной benchmark provenance.

Установка:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r resources/requirements.lock
```

Запуск Ollama:

```bash
ollama serve
ollama pull qwen2.5:14b
```

Перед созданием Workflow приложение проверяет:

- доступность сервера Ollama;
- точное наличие выбранной модели;
- model digest;
- список capabilities;
- наличие capability `tools`;
- версию Ollama server.

Если проверка не пройдена, запуск завершается до обращения к pipeline.

## 4. Интерактивный режим

Минимальная команда:

```bash
python visa_cli.py --model qwen2.5:14b
```

Полностью явная конфигурация:

```bash
python visa_cli.py \
  --model qwen2.5:14b \
  --ollama-url http://localhost:11434 \
  --workflow-db reports/local/conversation.db \
  --report-db reports/local/interactions.db \
  --report-xlsx reports/local/interactions.xlsx
```

Параметры:

| Параметр | Назначение |
|---|---|
| `--model` | Точное имя установленной Ollama-модели |
| `--ollama-url` | Адрес REST API и inference runtime |
| `--workflow-db` | Agno SQLite history для follow-up контекста |
| `--report-db` | SQLite с результатами и телеметрией |
| `--report-xlsx` | Производный XLSX-отчёт |
| `--debug` | Подробный trace агентов и инструментов |

`--debug` может вывести вопросы, аргументы инструментов, фрагменты evidence и
сырой модельный текст. Его следует включать только в безопасной локальной
среде. Сырой ответ финального Manager не печатается до применения policy
checks даже в debug-режиме.

Обычные приветствия обрабатываются без запуска исследования. Для
содержательного вопроса используется текущая conversation session. Команды
`/new_run` и `/change_model` создают новый experiment run и новый session ID,
поэтому независимые эксперименты не смешивают историю.

## 5. Benchmark

Benchmark-конфигурация — JSON с версией, сценариями и ходами диалога. Сценарий
имеет тип:

- `independent` — один независимый ход;
- `follow_up` — несколько связанных ходов в одной session.

Каждый ход может содержать semantic expectations:

- `required_pattern_groups` — AND между группами и OR внутри группы;
- `forbidden_patterns` — выражения, которых не должно быть в ответе.

Запуск:

```bash
python benchmark_runner.py \
  --model qwen2.5:14b \
  --questions resources/benchmark_questions.json \
  --db reports/benchmark/report.db \
  --xlsx reports/benchmark/report.xlsx \
  --workflow-db reports/benchmark/history.db
```

Runner создаёт уникальный namespace для invocation. Независимые сценарии
получают разные session IDs; ходы одного follow-up сценария используют одну
session. Это сохраняет необходимый контекст и исключает перенос истории между
несвязанными вопросами.

Результат одного хода оценивается по трём уровням:

| Уровень | Что означает |
|---|---|
| Technical | Workflow и обязательные шаги завершены; evidence и citations прошли проверки |
| Semantic | Ответ соответствует regex-ожиданиям конкретного сценария |
| Release | Одновременно пройдены technical, semantic и safety требования |

Процесс возвращает код `0`, только если каждый ожидаемый ход записан и каждый
release check прошёл. Неполный прогон, ошибка XLSX export или отсутствующий
результат проверки дают ненулевой код.

## 6. Evidence record/replay

Live web меняется: выдача поиска, содержимое страниц и доступность документов
могут отличаться между двумя запусками. Для сравнения моделей на одинаковом
входе предусмотрены режимы:

- `live` — обычный поиск;
- `record` — поиск плюс атомарная запись evidence manifest;
- `replay` — запуск на ранее сохранённом evidence без сетевого retrieval.

Manifest связывает:

- версию schema;
- версию Workflow, prompts, collector и benchmark;
- digest benchmark-конфигурации;
- идентификаторы сценария и хода;
- hash исходного prompt;
- точный поисковый запрос;
- документы и их content hashes;
- hash каждого пакета;
- hash всего manifest.

Record mode не перезаписывает существующий manifest. Replay mode проверяет
целостность и совместимость до использования данных. Во время replay также
используется сохранённый поисковый запрос, поэтому Query Builder второй модели
не меняет экспериментальный вход.

## 7. Отчёты

`ExperimentReporter` записывает данные сначала в SQLite. После транзакции он
атомарно пересобирает XLSX.

SQLite хранит:

- конфигурацию и версии experiment run;
- вопросы, ответы, статусы и длительности;
- результаты каждого шага;
- фактические tool calls и их ошибки;
- прочитанные source IDs;
- citation, safety и benchmark metrics;
- model/runtime/evidence provenance.

XLSX содержит листы:

- `Benchmark Summary`;
- `Runs`;
- `Interactions`;
- `Step Outputs`;
- `Tool Calls`.

Строки, начинающиеся с Excel formula prefixes, экранируются. Недопустимые
control characters удаляются. Ошибка XLSX не откатывает уже сохранённую
SQLite-транзакцию, но benchmark считается неуспешным, поскольку ожидаемый
артефакт не создан.

## 8. Сеть, данные и приватность

Framework telemetry Agno отключена у Agents и Workflow. Локальная телеметрия
проекта остаётся включённой и сохраняется в указанные SQLite/XLSX файлы.

Live mode не является offline:

- поисковая формулировка отправляется поисковому провайдеру DDGS;
- HTTPS-запросы выполняются к государственным сайтам;
- сетевым сторонам видны обычные метаданные соединения.

Не помещайте PII, номера документов, адреса, даты рождения или секреты в
вопросы и поисковые формулировки. Файлы в `reports/` следует считать
чувствительными и не публиковать без проверки.

## 9. Ограничения

- Официальные страницы могут менять адреса и разметку или блокировать
  автоматическую загрузку.
- Динамический HTML и сложные PDF могут извлекаться неполно.
- Разрешённые домены ограничивают полноту поиска намеренно.
- Локальная модель может неверно интерпретировать evidence или не соблюдать
  tool protocol; такие случаи должны завершаться ошибкой, но невозможно
  детерминированно проверить весь смысл текста.
- Regex semantic checks измеряют конкретные ожидания сценария, а не полную
  юридическую корректность.
- Safety filter покрывает известные практические формулировки и не заменяет
  полноценную модерацию или human review.
- Система не определяет личную eligibility и не предсказывает решение
  государственного органа.
