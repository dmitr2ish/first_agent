# Дизайн Visa Research Workflow

## 1. Основная идея

Система разделяет вероятностную работу LLM и детерминированные обязательные
условия.

LLM хорошо подходит для:

- преобразования follow-up вопроса в самостоятельный запрос;
- поиска релевантных фрагментов внутри ограниченного набора документов;
- объяснения и сравнения фактов естественным языком.

Python-код лучше подходит для:

- выбора допустимых сетевых адресов;
- ограничения размеров и числа документов;
- регистрации фактических вызовов tools;
- проверки source IDs и hashes;
- остановки pipeline при нарушении контракта;
- сохранения воспроизводимых метрик.

Дизайн не пытается сделать prompt единственной защитой. Существенное правило
дублируется программным контролем там, где это возможно.

## 2. Цели

### 2.1. Grounding по реально прочитанным документам

Наличие источника в пакете ещё не означает, что агент его прочитал. Поэтому
tool telemetry связывает каждую цитату с успешным
`read_official_source` или непустым результатом
`search_official_sources`.

### 2.2. Проверяемая цепочка преобразований

Поисковый запрос, пакет документов, исследовательский отчёт, citation check,
валидированный отчёт и финальный ответ существуют как отдельные результаты
шагов. Ошибку можно локализовать, не анализируя один непрозрачный LLM-вызов.

### 2.3. Fail-closed поведение

Когда обязательное доказательство отсутствует, система не дополняет ответ из
памяти модели. Шаг возвращает `success=False` и `stop=True`. Это относится к:

- пустому вопросу или поисковому запросу;
- ошибке или пустому результату retrieval;
- отсутствию фактического evidence read;
- пустому исследовательскому или проверенному отчёту;
- недопустимым source IDs и URL;
- потере grounding в финальном ответе.

Если safety policy обнаруживает опасную практическую инструкцию, модельный
текст заменяется детерминированным отказом. Затем отказ проходит те же
citation и grounding checks; нарушение этих контрактов уже останавливает шаг.

### 2.4. Воспроизводимость сравнения моделей

Каждый benchmark run хранит версию кода, конфигурацию модели, digest набора
сценариев и runtime metadata. Record/replay позволяет отделить различия
моделей от изменений live web.

## 3. Границы доверия

### Пользовательский ввод

Считается недоверенным. Он может содержать ошибочные утверждения, prompt
injection, PII или просьбу о противоправных действиях. Ввод используется как
данные, а не как инструкция, способная изменить системные правила.

### Содержимое веб-страниц

Также считается недоверенным. Даже разрешённый официальный домен может
содержать пользовательский текст, неожиданный markup или инструкции,
которые не должны управлять агентом. Researcher и Validator получают явное
указание игнорировать инструкции внутри evidence.

### Языковая модель

Не является доверенным enforcement-компонентом. Её tool calls, текст и
цитаты проверяются после выполнения.

### Локальный Python-код и manifests

Являются enforcement boundary проекта. При этом manifest считается
доверенным только после проверки schema и всех связанных SHA-256.

## 4. Получение источников

Collector разрешает только HTTPS URL, у которых hostname равен разрешённому
домену или является его поддоменом. Простого строкового suffix недостаточно:
адрес вроде `uscis.gov.example.com` отклоняется.

Redirect выполняется вручную. Каждый следующий URL проверяется до запроса,
что предотвращает уход с разрешённого сайта через redirect.

Дополнительные ограничения:

- не более пяти redirect;
- ограниченный размер загрузки;
- только поддерживаемые content types;
- нормализация и ограничение длины текста;
- deduplication URL;
- ограниченное число источников;
- SHA-256 точного извлечённого текста;
- SHA-256 канонического evidence package.

Поддерживаются HTML, plain text и PDF. Для HTML используется основной
экстрактор и fallback через BeautifulSoup.

## 5. Контроль инструментов

Researcher имеет инструменты:

- `list_official_sources`;
- `search_official_sources`;
- `read_official_source`.

Validator имеет:

- `check_source_ids`;
- `search_official_sources`;
- `read_official_source`.

`list_official_sources` и `check_source_ids` показывают метаданные, но не
считаются чтением содержания. Evidence read засчитывается только для:

- успешного `read_official_source` с непустым `content`;
- успешного `search_official_sources` с непустым `matches`.

Если агент не прочитал evidence с первой попытки, контроллер делает один
повтор с прямым требованием начать с чтения. Вторая неудача завершает шаг.
Скрытые внешние retries для этих шагов не используются.

## 6. Citation invariants

Источник получает локальный ID `S1`, `S2`, ... только внутри текущего пакета.
Цитата имеет строгий формат `[S1]`.

Проверяются следующие инварианты:

1. ID существует в текущем пакете.
2. Researcher реально прочитал этот источник.
3. Validator не добавил ID, которого не было в исследовательском отчёте.
4. Validator не добавил URL.
5. Финальный ответ не добавил новый ID.
6. Финальный ответ не потерял требуемые citations.
7. Source appendix содержит только источники, процитированные в теле ответа.

URL из модельного текста удаляются. Проверенный список ссылок строится
Python-кодом из source package, поэтому модель не выбирает конечный URL.

## 7. Финальный ответ и безопасность

Manager получает только проверенный отчёт и формулирует ответ на языке
пользователя. После него выполняются:

- проверка пустого ответа;
- проверка новых, потерянных и неверно оформленных source IDs;
- удаление model-authored URL;
- safety assessment;
- добавление локализованного legal disclaimer;
- добавление списка процитированных официальных источников.

Safety policy блокирует практические советы по подделке документов,
сокрытию фактов, взяткам, фиктивным отношениям и иным формам
иммиграционного мошенничества. Проверка учитывает отрицание и предупреждение,
чтобы законный отказ не блокировался как опасная инструкция.

Фильтр намеренно узкий. Его задача — жёстко остановить известные опасные
паттерны, а не классифицировать весь возможный вред.

## 8. История диалога и изоляция

Follow-up вопросы требуют истории, но независимые эксперименты не должны её
разделять.

- CLI создаёт process namespace и новый session ID для каждого experiment
  run.
- Независимые benchmark-сценарии получают разные session IDs.
- Ходы одного `follow_up` сценария сохраняют общий session ID.
- Benchmark history DB можно задать явно; иначе создаётся отдельный файл
  рядом с reporting DB.
- Явный namespace нормализуется и получает hash-суффикс, чтобы длинные
  значения с одинаковым префиксом не сталкивались.

## 9. Reporting design

SQLite — первичный артефакт, потому что поддерживает транзакции, точные типы,
связи между сущностями и повторную генерацию представления. XLSX — удобный
read-only view для анализа человеком.

Запись одного результата устроена так:

1. нормализуются step outputs и tool telemetry;
2. вычисляются technical, semantic и release критерии;
3. interaction и tool calls сохраняются в одной SQLite-транзакции;
4. XLSX строится во временном файле;
5. готовый файл атомарно заменяет предыдущий.

Formula-like строки экранируются перед записью в Excel. Это важно, потому что
вопросы, ответы и web content являются недоверенными данными.

## 10. Benchmark design

Сценарий задаёт не ожидаемый полный ответ, а минимальные semantic свойства.
Так тест остаётся устойчивым к стилю и языковой вариативности, но проверяет
важные различия: immigrant/nonimmigrant, исправление ложной предпосылки,
сохранение контекста, признание недостатка данных.

Release pass вычисляется только при одновременном выполнении всех обязательных
условий. `None`, отсутствующая строка результата или неполное число ходов не
интерпретируются как успех.

## 11. Privacy design

Agents и Workflow создаются с `telemetry=False`; проект не отправляет trace во
внешнюю framework telemetry. Но локальные отчёты намеренно подробны, а live
retrieval использует сеть.

Безопасная эксплуатация предполагает:

- не передавать PII;
- хранить `reports/` локально;
- включать `--debug` только при необходимости;
- проверять артефакты перед публикацией;
- использовать отдельные DB для независимых сравнений.

## 12. Не-гарантии

Проект не гарантирует:

- юридическую правильность и полноту ответа;
- актуальность документа после момента загрузки;
- корректное извлечение каждой динамической страницы или PDF;
- одинаковый live evidence в разные моменты времени;
- поддержку модели только на основании её размера;
- защиту от всех возможных вредных формулировок;
- определение личной eligibility или результата рассмотрения дела.
