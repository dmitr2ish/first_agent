# Реализация этапа 1: подробное объяснение

## 1. Что изменилось простыми словами

До изменения Researcher получал весь текст официальных страниц прямо в
сообщении. Это похоже на ситуацию, когда ученику сразу выдают стопку книг и
просят написать ответ, но преподаватель не может понять, какие страницы ученик
действительно прочитал.

После изменения Researcher получает библиотечные инструменты:

- посмотреть каталог документов;
- найти нужные слова во всех документах;
- прочитать выбранный фрагмент.

Теперь в терминале можно увидеть, какой инструмент агент выбрал, с какими
аргументами его вызвал и какой результат получил.

## 2. Архитектура до изменения

Раньше данные проходили так:

```text
Source Collector
    ↓
полный source_package вставляется в prompt
    ↓
Researcher получает вопрос и все страницы одновременно
    ↓
Researcher пишет отчёт
```

Проблемы этого подхода:

1. нельзя доказать, что модель прочитала конкретный источник;
2. невозможно посчитать реальные обращения к evidence;
3. prompt содержит много нерелевантного текста;
4. большой prompt медленнее обрабатывается;
5. модель может ответить из внутренних знаний, а не из источников.

## 3. Архитектура после изменения

Теперь цепочка выглядит так:

```text
Source Collector создаёт source_package
    ↓
source_package передаётся в dependencies
    ↓
Researcher получает вопрос и описания tools
    ↓
list_official_sources()
    ↓
search_official_sources(...) и/или read_official_source(...)
    ↓
Researcher получает только нужные evidence
    ↓
Researcher пишет отчёт с [S1], [S2], ...
```

Главная идея — отделить инструкцию для LLM от данных, которыми управляет
Python-код.

## 4. Что такое tools в Agno

Tool — обычная Python-функция, которую Agno показывает языковой модели как
доступное действие.

Researcher создаётся с тремя функциями:

```python
tools=[
    list_official_sources,
    search_official_sources,
    read_official_source,
]
```

Agno читает:

- имя функции;
- docstring;
- параметры и их типы;
- обязательные аргументы.

Из этого Agno создаёт JSON-схему tool и передаёт её Ollama. Модель может вернуть
не обычный текст, а структурированный запрос, например:

```json
{
  "name": "read_official_source",
  "arguments": {
    "source_id": "S2",
    "start_char": 0,
    "max_chars": 1000
  }
}
```

Agno вызывает соответствующую Python-функцию и отправляет результат обратно
модели.

## 5. Что такое `dependencies`

`dependencies` — служебные данные конкретного запуска агента. Они доступны
Python-инструментам, но не вставляются автоматически в пользовательский prompt.

Researcher запускается так:

```python
researcher.run(
    prompt,
    stream=False,
    dependencies={
        "source_package": source_package,
    },
)
```

Когда модель вызывает tool, Agno передаёт функции объект `RunContext`.
Инструмент получает source package:

```python
dependencies = run_context.dependencies or {}
source_package = dependencies.get("source_package")
```

Если package отсутствует или имеет неправильный формат, функция выбрасывает
понятный `ValueError`. Это лучше, чем неявная ошибка позднее в процессе чтения.

## 6. Как работают три инструмента

### 6.1. `list_official_sources`

Инструмент возвращает метаданные:

```json
{
  "source_id": "S2",
  "title": "Chapter 2 - Eligibility for O Classification - USCIS",
  "url": "https://www.uscis.gov/...",
  "document_type": "html",
  "content_length": 3122
}
```

Полный `content` не возвращается. Это только каталог. Поэтому один вызов `list`
не доказывает, что агент прочитал evidence.

### 6.2. `search_official_sources`

Инструмент ищет слова внутри уже загруженных документов. Он не выполняет новый
интернет-поиск.

Этапы поиска:

1. строка запроса переводится в единый регистр;
2. запрос разбивается на значимые слова;
3. слова ищутся в каждом источнике;
4. источник получает score по числу совпадений;
5. вокруг первого совпадения формируется excerpt;
6. результаты сортируются по score.

`max_results` ограничивается диапазоном от 1 до 10.

### 6.3. `read_official_source`

Инструмент читает часть конкретного документа:

```python
read_official_source(
    source_id="S2",
    start_char=0,
    max_chars=1000,
)
```

Защитные ограничения:

- отрицательный `start_char` превращается в `0`;
- минимальный размер результата — 500 символов;
- максимальный размер результата — 8000 символов;
- `source_id` сравнивается без учёта регистра;
- неизвестный ID возвращает JSON с ошибкой и списком доступных ID.

Эти ограничения защищают контекст модели и делают поведение предсказуемым.

## 7. Как работает трассировка

Researcher настроен так:

```python
tool_hooks=[trace_tool_call]
```

Hook оборачивает настоящий вызов функции:

```text
запомнить время начала
    ↓
напечатать имя и аргументы
    ↓
вызвать настоящий tool
    ↓
напечатать результат
    ↓
напечатать длительность
    ↓
вернуть результат модели
```

Пример реального вывода интеграционной проверки:

```text
[🔧 TOOL CALL] Tool: search_official_sources
[🔧 TOOL CALL] Arguments:
{
  "query": "O-1A visa criteria",
  "max_results": "5"
}
[✅ TOOL RESULT] search_official_sources
{
  "query": "O-1A visa criteria",
  "matches": [...]
}
[⏱ TOOL TIME] 0.000s
```

Это доказывает, что функция действительно выполнялась. Одна фраза модели
«я изучил источники» такого доказательства не даёт.

## 8. Зачем установлен `tool_call_limit=8`

Без лимита модель может многократно повторять поиск и чтение. Лимит защищает от:

- бесконечного цикла;
- слишком долгого запуска;
- переполнения контекста результатами tools;
- непредсказуемого расхода ресурсов.

В интеграционной проверке понадобилось только три вызова, поэтому лимита восемь
достаточно для нормального исследования нескольких документов.

## 9. Что показала интеграционная проверка

Проверка отвечала не на вопрос о качестве юридической консультации, а на вопрос
о правильности технической цепочки.

Она показала следующее:

1. Ollama доступна и модель `qwen2.5:14b` поддерживает tools.
2. Query Builder создал английский поисковый запрос.
3. Source Collector загрузил пять официальных страниц USCIS.
4. Agno передал модели схемы всех трёх tools.
5. Модель вызвала `list`, `search` и `read`.
6. Каждый вызов получил правильный `source_package` через `RunContext`.
7. Hook вывел имя, аргументы, результат и время.
8. Researcher написал непустой отчёт с citations.
9. Validator и Manager получили результат и завершили Workflow.
10. Python-процесс завершился с кодом `0`.

Следовательно, этап 1 проверяет не обещание модели, а работоспособность
механизма tool calling от начала до конца.

## 10. Как самостоятельно повторить проверку

### 10.1. Unit-тесты

Из корня проекта:

```bash
venv/bin/python -m unittest discover -s tests -v
```

Ожидается:

```text
Ran 7 tests
OK
```

### 10.2. Проверка Ollama

```bash
curl http://localhost:11434/api/tags
```

В данных модели должна присутствовать capability `tools`. Для проверенного
запуска использовалась `qwen2.5:14b`.

### 10.3. Интерактивный запуск

```bash
venv/bin/python visa_workflow.py
```

После выбора модели можно задать вопрос:

```text
Какие официальные критерии USCIS установлены для визы O-1A?
```

В stdout необходимо найти:

```text
[🔧 TOOL CALL] Tool: list_official_sources
[🔧 TOOL CALL] Tool: search_official_sources
```

или:

```text
[🔧 TOOL CALL] Tool: read_official_source
```

После tool calls должен появиться непустой отчёт с `[S1]`, `[S2]` и другими
реальными source IDs.

## 11. Что первый этап ещё не гарантирует

Инструкция «обязательно вызови tool» остаётся инструкцией для LLM. Другой
запуск модели теоретически может её нарушить.

Первый этап предоставляет инструменты и наблюдаемость. Этап 2 добавит
детерминированную программную проверку:

- сколько tools вызвано;
- какие имена использованы;
- были ли ошибки;
- выполнялось ли чтение evidence;
- нужно ли завершить шаг ошибкой или сделать один retry.

Также Validator пока получает полный source package в prompt. Его перевод на
tools относится к этапу 4.
